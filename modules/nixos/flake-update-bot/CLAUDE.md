# flake-update-bot

`t11s.flakeUpdateBot` runs `pkgs.t11s.flake-update-bot` weekly on the host that also runs Hydra (juicy-j). The orchestrator is `packages/flake-update-bot/flake-update-bot.sh`; its Hydra logic is covered by `bash packages/flake-update-bot/tests.sh`.

- It works in its own clone at `/var/lib/flake-update-bot/repo`, on branch `flake-update`, and never merges.
- Hydra is the gate: the bot pushes, then polls Hydra's JSON API for the evaluation of that commit. Hydra polls the branch itself (jobsets are declared in `systems/x86_64-linux/juicy-j/hydra.nix`).
- On failure it runs headless `claude` with a profile shipped in the package: `claude-settings.json` (permissions and sandbox), `claude-instructions.md` (appended to the system prompt) and `fub` (`fub.sh`). Claude gets its own `CLAUDE_CONFIG_DIR`, and project and local settings are ignored.
- Claude's shell runs in Claude Code's bubblewrap sandbox: no network, no Nix daemon, home and `/run/credentials` hidden, writes only inside the clone. `fub` is the one command excluded from the sandbox; it has a fixed set of subcommands (`build`, `log`, `eval`, `input-path`, `hold-back`, `fmt`, `commit`) with validated arguments. Adding a subcommand widens what an unattended agent can do outside the sandbox, so keep them narrow and never accept arbitrary shell or Nix expressions. `fub` only escapes the sandbox when it is the whole command; combined with pipes or `;` it runs inside and cannot reach Nix.
- Limits of that isolation: it runs as the main user in the same unit as the secrets. Claude's own Read tool is restricted by deny rules (all of home, the credential directories), not by the sandbox, and `fub` runs with full access. The clone lives in `/var/lib` so that denying home does not hide it. The orchestrator still redacts credential values from PR comments, refuses to push a commit containing one, and does the pushing itself, to github.com only.
- Manual run: `sudo systemctl start flake-update-bot`, then `journalctl -fu flake-update-bot`.
- To test against an existing `flake-update` branch without updating the lock, set `FUB_SKIP_UPDATE=1` through a runtime drop-in.
- The `flake-update` branch must keep existing on GitHub. When it is missing, Hydra's fetch for that jobset hangs for its full ten-minute timeout on every poll and holds the lock on the shared clone, which delays `master` evaluations behind it (seen 2026-10-01; root cause inside Hydra's environment not identified). Do not delete the branch after merging a PR; the bot recreates it on its next run if it is gone.
